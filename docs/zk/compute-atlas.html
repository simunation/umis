What happens as the network grows

Why one line climbs

Every node applies every beacon block, so every node verifies every zone's proofs. The number of proofs grows with the number of zones, and per-node verification grows with it. Proving is spread across members, so each node's proving load stays roughly flat.

With recursive aggregation, the beacon chain checks one proof per slot. The work moves to aggregator nodes, and aggregation itself is proving, so it parallelises and can run on a GPU.

Preview: the same recipe for Game of Life

A local rule per zone or per cell maps cleanly onto this pipeline. One cell is one bit; its next state is rule[state][count of 8 neighbours]. A Born/Survive rule is 18 bits, so each cell's rule id can sit in a preprocessed column, or be a public input when rules change at runtime.

  • No division or remainder, and no 16-bit range checks: the floor-division columns go away.
  • The count is a linear sum, so it needs no constraint degree. The next state is one LogUp lookup into a table of (rule, state, count, next).
  • Neighbour reads use the same memory bus, with 8 single-value reads instead of 6 reads of 4 values.
  • The simulation stays negligible; proving still dominates. The levers on this page apply unchanged.
